## Four things we found while testing

These are all minor, and two of them are data rather than API issues. Listing them because
they changed how we had to write our client.

**1. An unknown area is now ignored rather than refused, and that is easy to miss.**
`GET /schools/search?name=Kidzee&city=Delhi&area=Zzqxville` returns `200` with
`"area_matched": false`, and the search quietly widens to the whole city. Before the update
it was a `404`.

Our area check read the status code, so the moment you shipped, it began reporting *every*
misspelt area as valid — the exact thing it existed to catch. We now read `area_matched`
instead, and we never file a school under the area we sent, only under the one you return.

Two questions: is `area_matched` a field we can rely on long term? And since you match areas
on the exact string, a typo now silently creates a second locality and splits one area's
schools — would you consider an opt-in strict mode that refuses an unknown area instead of
creating it? We would use it on every call.

**2. The `candidates` list looks capped at 5.** "Delhi Public School", "Kidzee" and
"DAV Public School" each return exactly 5 for Delhi, and DPS certainly has more. We had
assumed the list was every place a school of that name exists, and used it to rule out
localities — which would wrongly drop a school whose area happened to be sixth. We have
worked around it, but a total count, or a way to page through, would let us use the list
properly.

**3. School 8010 is broken in your data.** `GET /schools/search?name=DAV Public
School&city=Delhi` returns it as a candidate with `"area": null` and
`"slug": "/dav-public-school-"` — no city, no locality. That slug produces a dead profile
URL, so we now drop any school whose row is incomplete rather than publish a broken link.
Could someone fix that row? And is it worth a one-off check for how many others look like it?

**4. A padded name misses, which risks duplicates on your side.** `"Kidzee Preschool"` in
Delhi returns `not_found`, although `"Kidzee"` returns 5 matches. Competitor pages pad names
constantly, so we trim a short ladder of shorter names before calling you, and only ever
send a trimmed name to `/resolve`.

Worth checking whether `/resolve` uses the same matcher as `/search`: if it does, anyone
sending a padded name straight to it will create a duplicate of a school you already have.

Also, ids 7700 and 7712 are both "Kidzee" in Dwarka — your own duplicate rows. We take the
lower id when that happens.
